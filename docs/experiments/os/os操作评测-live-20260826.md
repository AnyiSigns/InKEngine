# OS 操作评测（live 真实桌面复核）

## 1. 实验/测试名称

OSWorld 风格 OS 操作评测 — live 真实桌面后端（Windows 真机；含 live 通道接线实现与缺口归因）

## 2. 实验效果

达标线：**简化集 ≥40%**。

| 口径 | 结果 | 达标线 | 判定 |
|---|---|---|---|
| **任务集 as-is（默认，最小化态按执行体 ack 记账）** | **1/3（33.3%）** | ≥40% | **未达标** |
| 严格口径（只认产品感知面回读，`INKLING_OS_LIVE_STRICT=1`） | 0/3（0.0%） | ≥40% | 未达标 |
| 适配口径（把断言改为产品面可观测证据：标题脏标记 / foreground 变更） | 1/3（33.3%） | ≥40% | 未达标 |
| **op 层可用性（7 个真实 OS op 是否可调用并生效）** | **6/7 生效、1/7 生效但阻塞、其中 1 个内容不可控** | 无门禁 | 通道可用，见 第七节 |

逐任务明细（as-is 口径，命令输出原文）：

| # | 任务 | 结果 | 输出说明 | 归因 |
|---|---|---|---|---|
| 1 | 计算器点击数字键 | FAIL | 「计算器未出现数字键 7」 | 感知面：UWP 计算器（`ApplicationFrameWindow`）子窗口仅 3 个框架窗口（`ApplicationFrameTitleBarWindow`×2、`ApplicationFrameInputSinkWindow`），无按钮级 HWND、无控件名、无矩形；且 `ui_click` 只接屏幕坐标 → 元素制断言不可闭环 |

| 3 | 窗口列表+聚焦+最小化 | PASS | 「窗口列表/聚焦/最小化 三操作生效」 | 三个 op 真实生效（外部量具 `IsIconic=True` 独立验证）；但 `window_list` 无 `minimized` 字段，故默认按执行体 ack 记账，严格口径下同一任务 FAIL（「最小化未生效」） |

## 7. live 通道现状核实、接线实现与失败根因

### 7.1 核实结论：任务书所述的调用形态与产品不符

| 面 | 实际形态（核实结果） |
|---|---|
| `inkling-headless` CLI | 参数为 `--round <text>` / `--op <engine_op> --args <json>` / `--audit export`；`--op` 经 `run_op` → `dispatch_op` → **仅引擎 op 注册表**（`call_engine_op` / `call_engine_op_async`），OS 工具名在此通道**不存在**。原 live 驱动使用的 `inkling headless --op <name> <json>`（子命令式、位置参数式）在产品中**从未存在** |
| OS 操作实体 | 桌面壳的**执行器**（`executors/impls.rs`），由 `fixtures/tools_os.json` 声明驱动注册（声明 ↔ 签名逐项校验，漂移即拒绝启动）；副作用经 `PlatformBackend` 的手写 user32/winmm FFI |
| 壳侧调用点 | `#[tauri::command] process_exec(tool, args, approved)`（`endpoint=process_exec` 的工具）、`#[tauri::command] device_mcp_call(tool, args)`（`endpoint=device_mcp`）、以及引擎桥回调 `os.dispatch`；三者均需**运行中的 Tauri 壳**（`State<ShellState>` + `ShellBackend(AppHandle)`） |
| 工具名与签名（与原 live 驱动逐项不符） | `launch_app{app}`（白名单 `notepad`/`calc`/`mspaint`，review）、`ui_tree_query{scope}`（allow，device_mcp）、`ui_click{x,y,button}`（**坐标制**，非 element_id，review）、`ui_type{text}`（**只打前台**，无 element_id，review）、`window_list{scope}`（review）、`window_focus{handle}`、`window_minimize{handle}`（**名字不是 focus/minimize**） |
| MCP 设备 server | `mcp/mod.rs` 的 `DeviceServer` 只服务 `endpoint=device_mcp` 工具（含 `ui_tree_query`），且**无独立 bin target**，仍需宿主进程内挂载 |
| 返回形状 | 执行器返回**字符串** `ExecOutcome.result`（`ui_tree_query`/`window_list` 是 JSON 文本，其余是中文人读文本，如「已启动应用: notepad」）；`launch_app` **不返回 window_id** |

结论：原 `LiveUIDriver` 的通道、工具名、参数、返回形状**四项全不符**，`--live` 在改造前 100% 不可能跑通。

### 7.2 接线实现（本次落地，未重构产品）

新增 CLI 第四条驱动面：`inkling-headless --os-op <tool> --args <json> [--approve]`

- 位置：`inkling/cli/src/lib.rs::run_os_op`（+39 行）、`inkling/cli/src/main.rs`（+25 行，新增 `--os-op` / `--approve`，命令名 `os_op`）；
- 实现取向「薄」：`include_str!` 复用壳的声明夹具 `fixtures/tools_os.json`（不复制签名）→ `build_registry_from_declarations`（保留声明 ↔ 签名一致性校验）→ `PlatformBackend` → `Authorization{approved}`，与壳 `process_exec` 走**同一套执行器与守卫**；
- **不装配引擎**（OS op 不经引擎 op 通道），故该路径无 Python 回合开销，单 op 端到端 29–182ms；
- 授权语义：壳内由引擎审批层判定后传 `approved`；headless 形态改由调用方 `--approve` 显式声明，**缺省 false 即 review 档 fail-closed**（实测无 `--approve` 时返回 `ok=false`、`kind=op`、「需 L2 人工审批后方可执行: window_list」，退出码 1）；
- 回归：`inkling/cli` 的 `cargo test` **5 passed / 0 failed**；壳 crate **零改动**（其执行器/注册表单测不受影响）；simulated 评测仍 3/3。

评测侧改造（`tools/benchmarks/bench_os_ops.py`，仅 `LiveUIDriver`；`SimulatedUIDriver` 与任务定义零改动）：
真实工具名/参数映射、HWND 层级 → 元素视图映射、`launch_app` 阻塞绕行、注入前 foreground 校验
（前台不是目标窗口即中止键盘注入，避免误注入他人窗口）、最小化态 ack/严格双口径开关。

### 7.3 op 层可用性实测（把「执行体是否生效」与「感知面能否回读」分开归因）

量具：自建 Tk 靶标窗口（主线程内记录键盘/鼠标事件到日志）+ 外部 `ctypes`（`IsIconic` / `GetWindowRect` / `SendInput`）。量具仅测量，不属产品面。

| op | 调用结果 | 副作用是否真的生效 | 独立证据 |
|---|---|---|---|
| `window_list` | 成功，29–105ms | 是 | 返回 137–153 窗口，含句柄/标题/类名/可见性 |
| `ui_tree_query` | 成功，39–121ms | 是（只读） | 前台句柄 + 顶级窗口 + 子窗口层级；记事本 → `Edit` + `msctls_statusbar32`；计算器 → 3 个 `ApplicationFrame*` |
| `window_focus` | 成功，90ms | 是 | 调用后 `ui_tree_query.foreground` == 目标句柄 |
| `window_minimize` | 成功，182ms | 是 | 外部 `IsIconic(hwnd) == True`、Tk 靶标 `state()=='iconic'`；产品面 `window_list` 仍报 `visible=true` 且无 `minimized` 字段 |
| `ui_click` | 成功，38ms | **是** | Tk 靶标记录 `CLICK (517,356)` **4/4 命中**（光标远置 (10,10) 组与预置目标组各 2 次全中，无竞态/无 DPI 偏移；产品 `SetCursorPos` 落点实测精确） |
| `ui_type` | 成功，51ms | **键事件到达，但内容不可控** | Tk 靶标收到 3 个 KEY 事件，字符为 `'??'` 随后落为 `'阿' '百' '川'`——注入经**中文 IME 转换**；同一靶标用 `SendInput`+`KEYEVENTF_UNICODE` 注入得到正确的 `'x' 'y' 'z'` |
| `launch_app` | **生效但永不返回** | 是（窗口 0.7–0.8s 出现） | 应用窗口已出现且进程存活，但 op 进程 12s 后仍未返回；根因见缺陷 3 |

### 7.4 失败明细与分类（含根因）

| # | 缺口/缺陷 | 分类 | 根因（代码位置） | 影响 |
|---|---|---|---|---|
| 1 | 感知面无控件矩形、无跨进程控件文本、无 UIA 元素名 | **机制缺陷（感知面能力不足）** | `backends.rs::windows_ui_ops::window_to_json` 只输出 `handle/title/class/visible/children`；`read_window_text` 用 `GetWindowTextW`（跨进程控件恒空） | 任务 1、任务 2 的元素级断言在真实面**不可闭环**（主因） |
| 2 | 窗口态无回读：`window_list` 无 `minimized`，`IsWindowVisible` 最小化后仍 true | **机制缺陷（感知面字段缺失）** | `backends.rs::windows_ui_ops::list_windows` | 任务 3 严格口径不可判定（ack 口径才 PASS） |
| 3 | `launch_app` / `open_file` 调用后**阻塞至被启动应用退出** | **机制缺陷（阻塞/无超时）** | `backends.rs::run_cmd` 用 `Command::output()`：被启动进程继承 stdout 管道写端 → 无 EOF → 永不返回；无超时保护 | headless 通道需绕行（DEVNULL + 轮询窗口 + kill）；**壳内同源代码同样阻塞引擎回合线程**（高危） |
| 4 | `ui_type` 无 IME 旁路 | **机制缺陷（注入实现）** | `backends.rs::windows_ui_ops::type_text` 用 `VkKeyScanW` + `keybd_event`（VK 制，经输入法） | 中文 IME 环境下输入内容被转换，文本不可控；任务 2 即便有回读也会失败 |
| 5 | `inkling/cli/.cargo/config.toml` 的 `PYO3_PYTHON` 相对层级错一级 | **环境错误（构建配置）** | 值为 `../../../.venv/...`，相对 `inkling/cli` 解析到仓库根**上一级**；壳的 `src-tauri` 才是三级 | 直接 `cargo build` 失败（`failed to run the Python interpreter`），须 env 覆盖 |
| 6 | headless 二进制运行期需 `pythonXY.dll` 可加载 | **环境错误（形态约束未文档化）** | 依赖 `inkling_shell_lib`（pyo3 `auto-initialize`），即使 OS op 路径不用 Python | 未加 PATH 时退出码 `0xC0000135`（DLL 未找到），无任何可读诊断 |
| 7 | 原 `LiveUIDriver` 通道/工具名/参数/返回形状全不符 | **任务集缺陷（评测侧）** | 改造前 `tools/benchmarks/bench_os_ops.py::LiveUIDriver` | `--live` 改造前必然 0%；已修复 |

**未达标（33.3% < 40%）责任归属**：任务 1、任务 2 的失败**不在执行体**（点击/输入/窗口三类执行体均实测生效），而在
①**感知面回读能力缺失**（缺 rect / 控件文本 / minimized，缺陷 1、2）与
②**输入注入未旁路 IME**（缺陷 4）；
任务集侧的元素级断言口径与真实面不同构（缺陷 7 的残留部分）放大了差距。
通道本身（本次接线）已验证可用：7 个 op 全部可调用，守卫链（声明校验 → 权限档 → 沙箱）完整生效。

## 8. 方案建议（不实施，供产品决策）

按性价比排序，均为壳侧局部改动，不动架构：

1. **`launch_app`/`open_file` 去阻塞**（缺陷 3，最高优先，属线上高危）
   `inkling/shell/src-tauri/src/executors/backends.rs::run_cmd`：对启动类操作改用
   `Command::spawn()` 且 `stdout/stderr = Stdio::null()`，或复用已有 `run_process_impl` 的超时+后台读管道模式。
   工作量：约 10–20 行 + 1 条单测（断言调用在被启动应用存活期间即返回）。
2. **`ui_tree_query` 补控件矩形**（缺陷 1，解锁元素→坐标闭环）
   同文件 `window_to_json` 增加 `rect: {left,top,right,bottom}`（`GetWindowRect`）；
   同步更新 `fixtures/tools_os.json` 描述（签名不变，输出内容扩展，注册校验不受影响）。
   工作量：约 15 行 + 1 条单测。实测意义：矩形是元素级点击缺失的**唯一必需环节**（其余环节已验证可用）。
3. **`window_list` 补窗口态**（缺陷 2）
   增加 `minimized: IsIconic(hwnd)`（可同时补 `maximized`/`zorder`）。工作量：约 8 行 + 1 条单测。
4. **`ui_type` 走 `SendInput` + `KEYEVENTF_UNICODE`**（缺陷 4）
   `windows_ui_ops::type_text` 改为 UNICODE 事件对，绕开 IME（本报告已用同法在同一靶标上验证正确性）；
   同时给 `GetWindowTextW` 类调用加 `SendMessageTimeout` 语义可顺带消除挂起窗口拖死枚举的风险。
   工作量：约 40 行（含 INPUT 结构体 FFI 声明）+ 2 条单测。
5. **控件文本回读**（缺陷 1 的另一半）
   跨进程控件文本需 `SendMessageTimeoutW(WM_GETTEXT)`（Win32 控件）或引入 UI Automation（UWP/WinUI）。
   注：实测 Win11 记事本的 `Edit` 子窗口连 `WM_GETTEXT` 也是空（编辑区不在该 HWND），
   故 UWP/WinUI 类应用的元素级评测**必须**走 UIA，属独立能力项（工作量数人日），建议单独立项推进。
6. **CLI 接线定稿化**（本次为实验接线，需产品定调）
   `--os-op` 的授权语义（`--approve` 由调用方自证）、是否只在开发构建暴露、审计落写是否补齐；
   另修 `inkling/cli/.cargo/config.toml` 的 `PYO3_PYTHON` 为 `../../.venv/Scripts/python.exe`（缺陷 5，一行）
   并在 README/文档补运行期 `pythonXY.dll` 的 PATH 约束（缺陷 6）。
7. **评测集口径分层**（评测侧，不动产品）
   建议把 live 任务分为「执行体面」（launch/focus/minimize/click/type 的 op 级断言，当前即可 100% 覆盖）
   与「元素面」（依赖 rect/UIA，按第 2、5 项能力解锁后启用），达标线分别判定，避免一条 40% 线同时考核两类能力。

5. 回归：`inkling/cli` 下 `cargo test`（期望 5 passed）+ simulated 评测（期望 3/3）。
