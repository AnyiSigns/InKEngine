# LLM 厂商适配层 & MCP 客户端审查（只读）

- 审查范围：`ink_engine/core/llm/*`、`mcp_client.py`、`runtime.py` 装配点、InKling 壳侧 `host.py`/`model_layers.py`/`bridge.py`/`mcp_service.py` 消费点、相关测试、`inkling/seed_data/tools.json`
- 审查依据：`.kilo/审查规则.txt`（调用链/依赖链/消费链逐层追溯；安全/正确性/冗余/质量属性四维度）
- 审查性质：只读，未修改任何文件
- 关键环境事实（已实测）：`mcp` 实装 **2.0.0**（非 1.x）；`ink_engine` 顶层 `pyproject.toml` 对 mcp 的下限为 `>=1.0`

---

## 一、问题清单（按严重级别）

### 阻塞（Blocker）

**阻塞一｜mcp 2.x 破坏性 API 更名未适配 — `mcp_client.py`**
- 问题：`streamablehttp_client` 在 2.x 已更名 `streamable_http_client`（下划线）；代码（含 `_HTTP_CLIENT_2X` 探测逻辑 :165）仍按 1.x 符号探测，2.x 下该符号不存在，探测直接抛 `ImportError`/`NameError`。同时 `CallToolResult` 在 2.x 仅 `is_error`（snake_case），无 `isError` 属性；`Tool` 字段为 `input_schema` 非 `inputSchema`。当前代码对 2.x 完全不可运行。
- 修正：以 `importlib.util.find_spec("mcp.client.streamable_http")` 判定，按版本分支适配 `streamable_http_client` / `is_error` / `input_schema`；建立 1.x 与 2.x 双路径或统一锁定 2.x 并全量更名。

**阻塞二｜模块级强依赖 mcp，违背“可选依赖”承诺 — `mcp_client.py` + `runtime.py:53`**
- 问题：`mcp_client.py` 在**模块级** `import mcp`，而 `ink_engine.core.runtime` 顶层 `from .mcp_client import McpClientManager, register_mcp_executor`（:53）。实测阻断 mcp 后 `import ink_engine.core.runtime` 直接失败，使整个引擎运行时无法导入——与模块 docstring“mcp 为可选依赖，导入不受影响”矛盾。
- 修正：将 mcp 相关 import 改为函数内惰性导入，`runtime` 仅持有 `McpClientManager` 类型/工厂的惰性句柄；缺 mcp 时 `McpClientManager` 构造显式抛 `OptionalDependencyError` 而非在导入期崩。

**阻塞三｜MCP server 实际连接缺失，工具声明名无 dispatch — `tools.json` + `mcp_service.py` + `exec_proc.rs`**
- 问题：`tools.json` 中 13 个 `endpoint=mcp` 工具（`server_id=inkling_exec`/`inkling_shell`），但全仓 python 侧**无任何 server 注册/连接代码**；`mcp_service.py` 仅为挂载编排提案，未建立到这两个 server 的真实连接。仅 Rust 侧 `exec_proc.rs` 引用了这两个文本 id。声明→调用分发的 server 实际未被 python 引擎连接，MCP 工具调用链为空。
- 修正：在 `McpClientManager` 中按 `tools.json` 的 `server_id` 建立真实 stdio/SSE 连接与生命周期管理，或将 MCP 工具从声明层下沉到 Rust 唯一实现侧并显式剔除 python 侧的悬空声明；二者须一致。

**阻塞四｜测试依赖已失效常量，mcp 2.x 下整组失败 — `tests/test_mcp_client.py:426-430`**
- 问题：用例直接引用 `mcp_client._HTTP_CLIENT_2X` 常量；该常量探测逻辑在 2.x 下抛异常（见 阻塞一），导致 `test_mcp_client` 整组不可运行，CI 对 MCP 层实际零覆盖。
- 修正：随 阻塞一 更名/重构探测逻辑后，将测试改为按 mcp 安装版本断言传输客户端类型，并 `importorskip` 保护。

### 严重（Critical）

**严重一｜双重重试逻辑叠加，放大 3×3=9 倍请求 — `fallback.py:43-54` vs `openai_compat.py:43-56`**
- 问题：`openai_compat` 内部已做 3 次重试（最大退避 4s），外层 `fallback.ModelChain` 又套 `RetryPolicy`（默认 attempts=3, max_delay=10s），退避上限与次数两处不一致且相互叠加，单次调用理论触发 9 次请求；属重复造轮子（规则三.1）。
- 修正：统一到单一重试层（`fallback.RetryPolicy` 为唯一权威），`openai_compat` 内重试默认关闭/仅作传输级兜底；退避上限、抖动策略集中配置。

**严重二｜流式路径不请求 `stream_options.include_usage`，用量计量全失 — `openai_compat.py`（`astream` 装配请求处）**
- 问题：`astream` 向 OpenAI-compatible 端点发起流式请求时未带 `stream_options={"include_usage": true}`。按规范，不带该参数服务端不在末帧回传 usage，导致流式路径 `LLMChunk.usage` 恒为空。主路径若为流式（InKling 多为流式），token 计费与用量观测在此路径完全丢失。
- 修正：`astream` 默认注入 `stream_options={"include_usage": true}`（可由 `LLMParams.extra_body` 覆盖/关闭），保证末帧 usage 被 `_parse_sse_line` 正确捕获。

**严重三｜`account_usage` 仅测试调用，生产用量闭环未打通 — `executor.py:329` / `graph.py:155`**
- 问题：`executor.account_usage` / `graph` 同名方法的唯一真实调用在 `tests/test_settle.py`（:481-487）；生产 LLM 消费点（host 的 `BehaviorLLM`/`collect_result`）未把 `LLMResult.usage` 喂入 `account_usage`。即便 严重二 修复，用量也不会进入计费/指标。
- 修正：在流式消费收尾处调用 `account_usage(result.usage)`（或 `collect_result` 聚合后统一上报），并补生产路径测试。

**严重四｜`llm_usage` 指标链名存实亡 — `bridge.py:1991-2005`、`metrics_snapshot`**
- 问题：`bridge.py` 声明并解析 `llm_usage` 帧（每帧 prompt/completion tokens），但 python/rust 全仓除测试 `test_metrics_snapshot.py` 外无任何生产点生成 `llm_usage`；指标快照读取恒为空/缺项，观测指标不真实。
- 修正：与 严重二/严重三 一并打通：由 LLM 用量产生 `llm_usage` 帧 → 桥接层收集 → 指标快照消费，形成闭环；或删除悬空契约。

**严重五｜`logging.redact` 前缀覆盖不全，存在凭据泄露面 — `logging.py:27-35`**
- 问题：redact 仅遮蔽 `sk-`/`bearer`/`key=` 等形态；`gsk_`/`AIza`/`xai-`/`pplx-` 等厂商 key 前缀未覆盖，且 `api_key` 若以裸键值出现在结构化日志字段/错误详情中可能无法被 `key=` 规则命中（规则一.3 脱敏要求）。
- 修正：扩展 redact 正则覆盖主流厂商 key 前缀；对结构化日志字段 `api_key` 做对象级遮蔽（参考 `errors.py` `_REDACT` 思路）。

**严重六｜`pyproject` mcp 下限过宽，与实际 API 不兼容 — `ink_engine/pyproject.toml`**
- 问题：mcp 可选依赖写为 `mcp>=1.0`，实装 2.0 且 API 破坏性更名（阻塞一）。下限允许 1.x 但代码按 2.x 假设（反之亦然），版本承诺不可信。
- 修正：锁定 `mcp>=2.0,<3` 或显式兼容双版本；CI 增加“无 mcp / mcp 2.x”两路矩阵。

**严重七｜`runtime.stop` 未显式 aclose LLM 链 — `runtime.py:512`**
- 问题：`stop` 仅关闭 `mcp_manager`/`storage`，未对 `engine_llm`（及其包装的 `CachingLLM`/`BehaviorLLM` httpx 连接）显式 `aclose`；依赖 GC 回收 httpx 客户端，长会话/重载时可能残留连接。
- 修正：`stop` 中 `await self.engine_llm.aclose()`（容错包裹），并在 `rebuild_engine`（:708）前先关闭旧链。

### 建议（Suggestion）

**建议一｜`enable_thinking` 经 `extra_body` 字符串透传，缺类型安全 — `bridge.py:1598` / `openai_compat.py`**
- 问题：`enable_thinking` 仅塞入 `LLMParams.extra_body` 通用通道，无结构化枚举；`extra_body` 仅按 `_CORE_PAYLOAD_FIELDS` 排除防覆盖，厂商特有参数（reasoning effort 等）无校验。
- 修正：将思考/推理类参数提升为 `LLMParams` 一等字段（如 `reasoning_effort`），适配层按厂商映射，降低误用风险。

**建议二｜`convert_mcp_tool` 应输出 OpenAI `parameters` 形态 — `mcp_client.py`**
- 问题：工具声明转换未显式将 `Tool.input_schema` 包装为 `{"type":"object","parameters": input_schema}`（OpenAI tool 约定），下游 `to_openai_tools` 消费契约可能错位。
- 修正：在 MCP→ToolSpec 转换处显式构造 `parameters` 键并校验 JSON Schema 合法性。

**建议三｜`_HTTP_CLIENT_2X` 探测机制脆弱 — `mcp_client.py:165`**
- 问题：靠捕获符号是否存在判定版本，符号名随版本漂移即失效（已发生在 2.x），且探测失败会污染模块导入。
- 修正：改用 `importlib.metadata.version("mcp")` 显式读取版本号分支；探测失败不得影响模块导入。

**建议四｜embeddings 缺超时/重试闭环 — `embeddings.py`**
- 问题：embedding 调用未复用 `openai_compat` 的传输异常分类与重试/超时（`httpx.Timeout`），网络抖动下无降级（规则四.1 健壮性）。
- 修正：复用 `openai_compat` 的传输层封装（或抽取共享 `_request_with_backoff`），统一超时与分类。

**建议五｜`astream` 不缓存而 `ainvoke` 缓存，语义不对称 — `cache.py:250/269`**
- 问题：缓存层仅对 `ainvoke` 命中复用，`astream` 直通不缓存；同一 prompt 在流式与非流式两条路径产生不同成本与延迟表现。
- 修正：明确流式不可缓存的边界条件（注释已说明），或在收尾收集完整流后回填缓存，保证一致性。

**建议六｜`McpClientManager` 缺健康检查与重连 — `mcp_client.py`**
- 问题：MCP 为长连接，当前无心跳/健康检查/断线重连；server 崩溃后调用静默失败（规则四.1/四.5）。
- 修正：增加连接存活探测与指数退避重连，失败上报结构化错误而非空结果。

**建议七｜`StubLLM` 与真实适配器行为可能漂移 — `bridge.py:1226`**
- 问题：测试用 `StubLLM` 替代真实 `openai_compat` 行为，若真实适配器变更（如 严重二 usage 帧），Stub 未必同步，回归测试失真（规则二.3）。
- 修正：核心链路以真实适配器 + `MockTransport` 验证，Stub 仅用于纯逻辑单测。

**建议八｜重试退避无抖动，存在惊群风险 — `fallback.py` / `openai_compat.py`**
- 问题：固定退避（无 jitter），并发调用同时重试会产生请求波峰。
- 修正：退避叠加随机抖动（如 `base * 2**n * (0.5~1.5)`）。

**建议九｜`tools.json` `server_id` 未与运行时注册表对账 — `tools.json` + `mcp_service.py`**
- 问题：声明层 `server_id` 与运行时实际可连接的 server 集合无校验，悬空 id 仅在调用时才失败。
- 修正：引擎装配期校验 `tools.json` 中 `server_id` 均存在于已注册 server 集，缺失即启动告警/阻断。

## 二、LLM 链观察

**架构评价（插拔性）**
- `registry.py` 的厂商注册以 `name → factory` 形式组织，新增厂商近似“插拔 U 盘”（规则四.3），`base.AsyncLLM` 抽象边界清晰，扩展成本可控。
- 但 `runtime` 对 `mcp_client` 的模块级硬依赖（阻塞二）打破了这一低耦合：可选能力的缺失不应拖累核心引擎导入。

**降级 / 重试 / 缓存闭环现状与重叠**
- 降级：`fallback.ModelChain` 提供多模型顺序降级，方向正确。
- 重试：存在**两套独立重试**（`openai_compat` 内 3 次 + `fallback` 外层 RetryPolicy），退避上限不一致（4s vs 10s），叠加放大至 9× 请求（严重一）。属典型“伪健壮”重复造轮子（规则三.1、四.6）。
- 缓存：`CachingLLM` 仅缓存 `ainvoke`、不缓存 `astream`，且缓存命中后 usage 的 `_tokens` 键被 security.strip 置空（`{"total_tokens": ""}`，`test_llm_cache.py:161` 显式断言为已知行为），但语义上缓存命中回合不计费（可接受，需文档化）。
- 闭环缺口：流式用量（严重二）→ 用量上报（严重三）→ 指标快照（严重四）三段均未接通，token 可观测性在主路径基本失效。

**MCP 工具契约缺口**
- 声明（tools.json 13 个 mcp 工具）→ 连接（python 侧无 server 连接代码）→ 消费（host 经 `convert_mcp_tool` 转 ToolSpec）三段断裂；真实执行体仅 Rust `exec_proc.rs` 持有 `inkling_exec`/`inkling_shell` 文本 id，python 引擎侧 dispatch 为空（阻塞三）。
- mcp 2.x API 更名（阻塞一）使 `mcp_client` 当前版本不可用，且测试因依赖失效常量整体失效（阻塞四），MCP 层实际处于“声明存在、运行不可达、测试不覆盖”的状态。

**安全面**
- 凭据入参 `repr=False` 与 `errors._REDACT` 对象级遮蔽做得较好（api_key 泄露面小）；但日志 redact（严重五）对多厂商 key 前缀覆盖不全，仍是潜在泄露点（规则一.3）。

**总体结论**
- 阻塞项集中于 mcp 2.x 适配与可选依赖承诺失效（阻塞一–阻塞四），需优先修复以恢复 MCP 层可运行与可测试；
- 严重项集中于“用量/指标闭环断裂”（严重二–严重四）与重试叠加（严重一），直接影响计费与稳定性观测；
- 建议项多为契约一致性、健壮性补强与去除重复逻辑，可在修复阻塞/严重项时一并收口。
