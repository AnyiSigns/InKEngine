## 复现结果

### 确定性复现（离线，权威）

通过 `debug_sandbox_extractor.py` 直接断言 `endpoint_operation` 与整条流水线，结果：

| 调用 | 提取器返回 | 流水线结果 |
|---|---|---|
| file_read op=read | `("read","a.txt")` | OK |
| file_write op=write | `("write","a.txt")` | OK |
| **file_edit op=edit** | **`None`** | **DENY：`操作提取器无法判定目标，拒绝执行（fail-closed）`** |
| file_write 缺 operation | `None` | DENY：同上 |
| file_write op=write 根内绝对路径 | `("write","<root>/a.txt")` | OK |

`file_edit` 的拒绝信息**与跑批报告完全一致**，且为**模型无关**——任何模型调用 `file_edit` 都会被同一个 fail-closed 出口拒绝。

### 真实模型复跑（live，poolside，--count 1）

- 修复**前**：成功率 100%（1/1，1 轮，耗时 45.72s）——该单任务 poolside 走 `file_write` 且 `operation` 合法，未触发 `file_edit`，故未暴露缺陷。
- 修复**后**：成功率 100%（1/1，1 轮，耗时 20.35s）——无回归。

结论：live 单任务未命中 `file_edit` 路径，无法以单次 live 复现「写操作被拒」；但缺陷在批量任务中必然出现于所有用到 `file_edit` 的回合，且对 `operation` 缺失/错写的写调用同样 fail-closed。确定性证据已完整覆盖。

## 定位结论（含证据：参数形态 vs 提取器判定）

根因 = **提取器判定对「合法操作别名」缺失**（engine 侧机制缺陷），非单纯「模型参数形态非法」。

1. **`file_edit` 永久 fail-closed（模型无关）**
   - `bench_complex_project.py:277-290` 将 `file_edit` 的 `operation` schema 定义为 enum `["edit"]`；
   - 但 `declarative_tools.py:79-87` 的 `_ENDPOINT_ACTIONS[FILE_OPS]` = `("read","write","delete","search","search_paths")`，**不含 `"edit"`**；
   - `endpoint_operation`（declarative_tools.py:287-302）对不在白名单的 operation 返回 `None` → `tool_pipeline.py:155-167` 输出「操作提取器无法判定目标」；
   - 同时权限层 `_DOMAIN_ACTIONS["filesystem"]` = `("read","write","delete")` 与文件沙箱 `FS_OPERATIONS`（sandbox.py:29）亦无 `edit`，即便提取器放行也会被权限/沙箱拒绝。
   - 证据：`file_edit op="edit"` 经 `endpoint_operation` 返回 `None`（确定性复现表），与跑批错误文案逐字一致。

2. **`file_write` 被拒 = 模型参数形态问题（非路径形态）**
   - 修复前的离线实验证明：`file_write op="write"`（合法）+ 根内相对/绝对路径，提取器与权限/沙箱**全部放行**；
   - 仅当模型**未给出或错写 `operation`**（如空串/遗漏）时返回 `None` → 同一 fail-closed 文案；
   - 因此「根内绝对路径」**不是**致因（提取器接受、沙箱按根解析通过）；致因是模型未稳定输出 `operation` 字段。
   - 证据：复现表中 `file_write op=""` → DENY，而 `op="write"` + 绝对路径 → OK。

### 分类

- 机制缺陷（高优先）：`file_edit` 的 `edit` 操作未被操作白名单/权限域/沙箱域接纳 → 永久 fail-closed。
- 模型行为（中优先）：poolside 偶发缺失/错写 `operation` 字段 → 合法写调用被同一 fail-closed 拒，且错误文案对模型无可指导性（未说明缺失/非法的是 `operation`）。

## 失败明细与分类

- F1（机制）：`file_edit` 的 `edit` 未被 `_ENDPOINT_ACTIONS[FILE_OPS]`、`_DOMAIN_ACTIONS["filesystem"]`、`FS_OPERATIONS` 任一接纳 → 永久 fail-closed。修复见下。
- F2（模型）：poolside 偶发缺失/错写 `operation` 字段 → 合法写调用被同一不可指导文案拒绝。属模型行为 + 错误反馈问题，非 engine 越权放宽可解。

## 根因与分类

- 类别：**机制缺陷（操作白名单不完整）+ 模型行为（operation 字段不稳定）**
- 根因：`file_ops` 操作语义在「工具声明（edit）」与「引擎白名单（read/write/delete/search/search_paths）」之间出现缺口；`file_edit` 自诞生起即无法通过声明式流水线（模型无关）。

## 修复决策与改动

- 决策：**允许修改**（仅限 `declarative_tools.py`，未触碰 sandbox.py/permissions.py 等其余仓库代码）。
- 改动：`endpoint_operation` 的 FILE_OPS 分支引入 `_FILE_OP_ALIASES = {"edit": "write"}`，在判定目标阶段将 `edit` 归一为 `write`。
  - 归一后：`edit` 复用既有 `filesystem:write:*` 权限与 `write` 沙箱根边界（语义等价：就地改写=写），不新增操作域；
  - 未知操作（chmod 等）与缺失 `operation` 仍返回 `None`，**fail-closed 不被破坏**；
  - 提取器返回的操作记为 `write`，审计/轨迹按既有 write 语义留痕（工具名仍为 `file_edit`，可追溯）。
- 验证：
  - 新增回归 `test_endpoint_operation_file_edit_alias`（`test_declarative_tools.py`）；
  - `pytest ink_engine/tests -k "sandbox or declarative or permission or approval" -q` → 112 passed；
  - 离线机制实验 6/6 通过；live poolside --count 1 无回归。
