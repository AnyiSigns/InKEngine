## 实验效果（指标 / 达标线）

### 一、沙箱/提取器机制断言（离线，mech_exp.py，6/6 通过）

| 编号 | 断言 | 期望 | 结果 | 实际 |
|---|---|---|---|---|
| M1 | file_edit(op=edit) 经别名归一后走 write 守卫放行 | OK | PASS | OK |
| M2 | file_write 缺 operation → fail-closed | DENY | PASS | DENY（操作提取器无法判定目标） |
| M3 | file_write 非法操作 chmod → fail-closed | DENY | PASS | DENY（操作提取器无法判定目标） |
| M4 | file_write 越界路径 /etc/passwd → 沙箱拒绝 | DENY | PASS | DENY（路径越界） |
| M5 | file_read 仅声明 read 权限，write 调用 → 权限未命中 | DENY | PASS | DENY（权限未命中） |
| M6 | file_write 根内绝对路径 → 提取器不拒、沙箱放行 | OK | PASS | OK |

结论：6/6 通过。fail-closed 对「缺 operation / 非法操作 / 越界路径 / 权限未命中」全部保留；`edit` 别名归一后与既有 `write` 守卫等价放行。

### 二、权限判定（filesystem:write:* 与根边界）

- 权限命中：`filesystem:write:*` × operation=write × 根内路径 → `ALLOW`（M1/M6）。
- 权限未命中：仅声明 `filesystem:read:*` 的工具发起 `write` → `DENY`（M5，权限层 `rule_matches` 按 action/pattern fnmatch，越界 `..` 段一律拒绝）。
- 边界由 `_AutoDefinitionSandbox`（declarative_tools.py:423-458）在每次校验时按 `endpoint_config["root"]` 现取 `FileSandbox` 判定，越界抛 `SandboxViolation`（M4）。

### 三、审批链 L0/L1/L2（引用既有测试族，运行结果）

- 测试族 `approval or bridge or permission` 运行：**64 passed**。
- L0（默认拒绝兜底）：`test_08_approval.py` — 超时默认拒绝、非法注入 `reject(source=invalid)`、`auto` 注入拒绝，均为 fail-closed（见 test_08_approval.py:80/111/116）。
- L1（review 委托挂卡）：`tool_pipeline.py:185-198` — 权限命中但门控分级 `review` 时委托 `approve_before_execute`，`DECISION_REJECT/TERMINATE` 拒绝并审计留痕。
- L2（沙箱验证 + 补丁链）：`test_bridge.py:104` — 未装配验证钩子 = fail-closed 拒绝，验证通过 + 批准才落链；验证不通过不静默降级（self_application.py:463 注释）。

## 失败明细与分类

- 无失败断言。相关测试族（sandbox/declarative/permission/approval）112 passed；approval/bridge/permission 64 passed。

## 根因与分类

- 机制层面：声明式流水线的操作白名单/权限域/沙箱域三处均缺 `edit`，导致 `file_edit` 结构性 fail-closed（模型无关）；该缺口已通过 `declarative_tools.py` 的 `_FILE_OP_ALIASES={"edit":"write"}` 在提取器层归一修复，未扩大操作域、未破坏既有 fail-closed 语义。
